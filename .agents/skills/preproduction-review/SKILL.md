# 생성 전 품질 검토

프로젝트 루트의 `docs/생성전-품질검토.md`를 읽고 `config/quality-rubric.json` 기준을 적용한다. 파일·체크박스의 존재를 품질 근거로 삼아 통과시킨 실패를 방지하는 프로젝트 전용 스킬이다. 최종 영상 제작·유료 재생성·새 계정·클라우드 호출을 허용하지 않는다. 사용자 범위와 기존 제작 지침을 우선한다.

## 기획과 검토를 구분

- NolanX의 샷 설계·동선·정체성·참조 스킬로 먼저 의도와 검증할 가설을 정한다. 기존 plan.json이 기준이다. 검토를 위해 새 콘셉트나 대본을 임의 확정하지 않는다.
- 도구 역할은 프로젝트의 docs/도구역할-선택기준.md를 따른다. 같은 플랫폼에서 생성했다는 이유로 일관성을 통과시키지 않는다. 다른 이미지·영상·음성 경로를 사용할 때도 채택 원본과 참조 호환, 실제 얼굴·의상·동작·음성 결과를 확인한다. 전용 기능 활용 여부와 검토 기준은 별개다.
- HyperFrames core·cli·studio 지침을 적용해 기존 자산으로 재생 가능한 미리보기를 준비한다. 영상이 필요한 자리에 정지 사진을 놓고 연속 동작을 검증했다고 하지 않는다.
- [화면·행동 설계](../../../docs/영상연출-설계기준.md)와 plan.direction을 확인한다. 새 정보·인물/소품 행동·카메라·주시점·소리·끝 상태를 시간별로 대조한다. layout_only와 애니매틱/동작 블로킹의 범위를 구별한다. 같은 사진의 확대·문구 교체를 실제 행동·연기 검증으로 통과시키지 않는다.
- 설계자 관점을 내려놓고 처음 보는 시청자 관점으로 검토한다. 같은 에이전트의 순차 관점 전환이며 별도 독립 심사·운동 전문가 검토가 아니다.

## 관찰할 것

1. 먼저 계획 설명을 가리고 실제 화면에서 누가 무엇을 하는지 서술한다. 의도는 그다음 읽고 관찰과 대조한다. 시청하지 않은 상태에서 blind review를 했다고 쓰지 않는다.
2. 전체 흐름, 각 장면, 모든 전환 양쪽, 준비·수행·복귀를 따로 평가한다. 좋은 얼굴·화질·자막으로 역할 혼동이나 동작 누락을 상쇄하지 않는다.
3. 무음·자막 제거 조건을 실제로 시험하거나 미시험으로 표시한다. 대사가 없을 때 행동을 이해하는지와 대사·행동의 시점 일치를 구분한다. 전사는 청취·립싱크 판정이 아니다.
4. 각 항목에 관찰 사실, 오해·반례 확인, 점수의 이유, 근거의 실제 시간·범위, 필요한 수정을 남긴다. 1~4점은 프로젝트 기준이며 흥행·전문가 점수가 아니다. 평균을 계산해 결함을 숨기지 않는다.
5. 실제로 본 프레임만 ai_visual로 기록한다. 자동 플레이어 시간 로그는 automation이다. 연속 동작은 직접 분석한 영상 또는 충분한 시간 간격의 실제 시계열 관찰로 검토한다. 접촉 시트만 작게 보고 정밀 관찰을 완료했다고 하지 않는다.
6. 못 본 것, 가려진 관절, 원본 저화질, 대역 마네킹, 아직 없는 음성·연기 등은 한계로 쓴다. 내부 참고 보드를 고객용 시범이나 생성 완료 품질로 전용하지 않는다.
7. visual_development는 전체 전개를, staging_performance는 모든 샷의 행동·도식·연기/동선을 실제 시간 흐름으로 관찰한다. 문장 반복·공허한 대기·무의미한 컷과 새 정보가 있는 유지 구간을 구별한다. 운동을 이해할 시간을 없애거나 전환 효과·음악으로 결함을 덮지 않는다. 고정 카메라·한 샷도 의미 있는 전개가 있으면 허용한다.

구도·조명의 이유는 director-visual-language로, 컷 양쪽의 화면 방향·행동 단계는 continuity-editing-axis-match로 보강할 수 있다. 영화용 감정·권력·동작 중 컷 권장을 운동 지도에 그대로 적용하지 않는다. 새 검사 항목이나 평균 점수를 늘리는 대신 기존 framing_focus·identity_role·transition 항목에서 실제 설명과 관찰을 구체화한다. 체크표가 완성돼도 시청자가 새로 알게 되는 내용·계속 볼 이유가 실제 화면에서 읽히는지 다시 판단한다.

## 기록과 재검수

`scripts/quality.py init/check/packet`을 사용한다. 새 검토는 pending에서 시작하며 도구가 점수를 자동 채우지 않는다. 기록·실제 파일 해시·계획과 미리보기의 버전·평가 범위를 연결한다.

- quality-review.json은 장면별 평가·실제 관찰·근거·결함·불확실성의 기준이다. reviews.json의 quality_review에 프로젝트 상대 경로로 연결한다.
- blocker·major는 수정 후 다른 실제 결과를 관찰하고 재검수하기 전까지 열린 상태다. `resolved`라는 단어만으로 닫지 않는다.
- 수정한 장면과 전환 양쪽, 영향받은 전체 흐름을 다시 검토한다. 변경 없는 근거를 무조건 폐기하지 말고 현재 버전과의 관계를 확인한다.
- HTML·참조·자막·폰트·JS·영상·기준 변경은 관련 품질 검토를 무효화한다. 해시를 새로 적는 행위 자체가 재검토는 아니다.
- 아직 생성해야 알 수 있는 품질은 해결됐다고 쓰지 않는다. 승인된 최소 시험 요청·성공 기준·현재 견적과 연결할 수 있을 때만 test_first로 관리한다. 고객 제시 전 확인할 항목을 남긴다.

`production.py check --stage design|generate`는 이 기록까지 확인한다. 품질 통과와 사용자 설계 채택·유료 실행 승인·운동 전문가 승인은 별개다. 현재 요청 범위의 환경 개선·로컬 검토는 끝까지 수행하고, 아직 승인되지 않은 생성 실행 직전의 한 번의 구체적인 검토 묶음으로 보고한다.

## 전달

“기술 검사 통과 / 내용·연출 판정 / 남은 결함·미확인 / 다음 수정과 영향 범위” 순서로 보고한다. 관찰한 사실과 추론을 구분한다. 통과를 늘리기 위해 기준을 낮추거나 모르는 항목을 통과시키지 않는다. 점검기는 기록을 검증하며 영상의 미감·정확성이나 AI 관찰의 진실성을 자동 보증하지 않는다.
